Requirements for the diff (item 6), all from this measurement:

- Compare reference fields by the identity of the matched target, not by name: comparing by name

- Exclude `CommentOnly`: it has no persistent handle and never matches.

## Orphan relations (fact, policy approved by Roberto)

- Typed OpenStudio accessors that return a related object directly segfault when the relation is
  absent: 74 (type, accessor) pairs over 65 fields in the corpus types
  (`validators/_fatal_references.py`, derived by `v0.3-evidence/blank_probe.py`). 31 call sites in
  17 curated functions use such accessors without a guard.
- `StandardsInformation:Material.material()` dies on 15 of 31 models, including FPM4 v9/v10 Proposed
  and the repo fixture `R2F-Office-Hub.osm`; no curated function calls it today.
- An empty Optional `.get()` raises `SystemError` or leaves an exception set that surfaces later.
- A reference to a non-existent handle is cleared by OpenStudio on load (logged), so after loading it
  looks like an empty reference. Text-level detection (`v0.3-evidence/ref_audit.py`) is outside v0.3.

Policy:

1. The generic reader uses only `getString`/`getTarget` (done, enforced by a contract test).
2. Curated functions never dereference a relation through a typed accessor without checking the
   field target first (pending, item 2).
3. Optionals are unwrapped only through `openstudio_toolkit._sdk.opt` (pending in `osm_objects`,
   item 2; contract test `test_no_bare_optional_get_in_osm_objects`).
4. Orphans are reported as `integrity.reference.absent` findings with `object_type="model"`; the
   `FindingObjectType` schema is not widened (done).

## Item 2: pattern and migration (session 2026-10-27)

Tests: `tests/osm_objects/test_dataframe_functions.py` (per function, found by introspection: empty
family has columns; fixtures with objects give the same columns; every `FATAL_WHEN_ABSENT` field blanked
on the fixtures, one subprocess per function, must not raise or die). `PENDING_MODULES` lists modules
not migrated yet (xfail, non-strict). Fixture for families no other fixture had (VRF, gas/steam/other
equipment, building units, exterior fuel/water, output variables): `tests/resources/extra_families.osm`,

Pattern (fact, verified by comparing every cell of every migrated function against d86d2c2 (before item 2) on
`small_office`, Office Hub and `extra_families` with `v0.3-evidence/compare_values.py`):

- Columns: a module-level `X_COLUMNS` tuple passed to `build_dataframe(..., columns=X_COLUMNS)`.
- Relations: keep typed accessors that return an Optional, through `_sdk.optional_name`. They return
  values inherited from default schedule/construction sets when the field is empty (e.g. 272 of 278
  surfaces in Office Hub take their construction from a set); reading the field instead loses them.
  Read through the field target (`_sdk.related_name`) only where the accessor returns the object
  directly and segfaults when empty (`FATAL_WHEN_ABSENT`). This refines policy 2 above.
- Topology fields that point to `OS:Connection` need one more hop (`thermal_zones._zone_air_node_name`).
- `FATAL_WHEN_ABSENT` misses combined cases: `ScheduleRuleset.summer/winterDesignDaySchedule()` fall
  back to the default day and segfault when both fields are empty (`schedules._design_day_schedule_name`).
- Node fields of 7 HVAC functions removed (Roberto's decision): chiller, coil cooling water, coil heating
  water, coil heating gas, air-to-air HX, AC VRF, and coil heating DX VRF. The accessors do not exist in
  OpenStudio 3.11 (AttributeError on Office Hub / `small_office`). The VRF heating coil fields exist in the
  IDD but were empty in all 104 coils of FPM4 Proposed and 65 of the VRF component library; the generic
  reader still exposes them.
- Construction layers: fixed columns `Layer 1`..`Layer 10` (Roberto, 2026-10-27). OpenStudio 3.11 refuses
  an 11th layer; the most seen in 400 local models is 7.

- `FATAL_WHEN_ABSENT` gained 5 pairs from a targeted probe on fresh objects (types absent from the
  corpus): `OS:Fan:OnOff` speed-ratio curves and `OS:ZoneHVAC:UnitHeater` fan, coil and availability
  schedule. Seven other direct `availabilitySchedule()` reads (fans, water/gas coils, fan coil) return the
  always-on schedule when empty and are safe.
- Zone equipment lists: at least 5 equipment slots (most seen per zone in 400 local models: 4; no
  OpenStudio limit), more if a zone has more. Same rule as construction layers.

State: item 2 implemented. All 21 modules migrated, every cell compared against d86d2c2 on the three
fixtures (identical, or an old crash now works); `PENDING_MODULES` is empty and both contract invariants
are "implemented".

raw OpenStudio `OptionalDouble` instead of the number (e.g. FPM4 Proposed: gross rated cooling and
heating capacity of the 17 VRF outdoor units; zone sizing factors in every `Sizing:Zone`). Four of them

OptionalDouble prints its value (or `''`), so old and new looked identical. `tests/dump` now asserts

## Item 5: compare (session 2026-10-27, approved by Roberto)

`analysis.compare.compare_to_mapping(model, mapping, by="space"|"thermal_zone", tolerance=1e-6)`, columns of
the contract's `[artifact.compare]`. Decisions (Roberto, 2026-10-27):

- Mapping = the shape `base_model_space_loads.py` (r2f-simulation-os) materializes: family -> {Space or
  Thermal Zone name -> absolute value}. Families `people`, `lights`, `electric_equipment` (dump names, so
  item 7 can cross compare with the diff). Absolute values only on the mapping side (people, W); a density
  is converted by the project's own glue before building the mapping. Outdoor air and extra fields
  (fraction radiant, subcategory) are outside v0.3 unless approved. `LoadMapping` lives in
  `analysis.compare`, so `apply` (item 4) imports it and compare never imports `transforms`.
- Compared value = the total OpenStudio resolves for the Space/Zone (what EnergyPlus simulates), not what
  is written on the load objects. A Thermal Zone is the sum of its Spaces, without the zone multiplier.
- `missing`: Space/Zone absent; or no load of the family reaches it and a non-zero value was requested
  (zero requested and nothing there is `match`); or a load that reaches it has no definition (orphan).
  `difference` = model - requested.

Facts (`v0.3-evidence/compare_check.py`, `compare_loads_measure.py`, `compare_inherit_probe.py`):

- Loads reach a Space from the Space and from one space type: its own, or the building's when the Space has
  none (replacement, not sum: a Space with its own type does not get the building type's loads). The
  BuildingStory level exists for default schedule/construction sets, not for loads. OpenStudio's totals
  handle every design method (absolute, per area, per person, area per person) and each load multiplier.
- Reading what is written would be wrong on Roberto's models. R2F-Office-Hub.osm: the record asks 5 W for
  `0.05-Storage`; the Space light has 5 W but the Storage space type adds 10.5 W (OpenStudio: 15.5 W).
  Office Hub reference-011: lights only on the 7 space types in W/m2, so every Space would look empty.
  FPM4 v10: 10-14 loads per family on space types; building space type OpenOffice set, though today all 105
  spaces have their own type. Roberto: only Office Hub followed the one-value-per-Space method strictly;
  FPM4/CCB43 mixed approaches (East Gate B2 unsure).
- OpenStudio's 1,908 Space and Zone totals on FPM4 v10 baseline/proposed, Office Hub actual-017,
  reference-011 and the example model equal, cell by cell, an independent recomputation from `dump_view`
  tables and records (inheritance, methods, multipliers). Same check in `tests/analysis/test_compare.py`
  on the three fixtures.
- An orphan load (empty definition field) makes `Space.lightingPower()` & co. raise `SystemError` (not a
  segfault); compare checks the field target first and reports `missing`.
- Cost: FPM4 Proposed v10, 315 rows, 0.02 s.
- Note: the 7-space lighting sample in Office Hub's parametrization record (section 3) predates `-006`;
  against actual-017 five of them "differ", while the model total (2,346.47 W) equals the current record.

State: item 5 implemented (contract status updated); `test_verification_runs_on_untouched_models` now
exercises compare by Space and by Thermal Zone. Suite: 409 passed, 11 xfailed.

### Shared objects: can they be split per Space? (Roberto, 2026-10-28; `v0.3-evidence/unshare_probe.py`)

Two different kinds of sharing:

1. **A definition used by several loads.** Fact: none in Office Hub actual-017, reference-011, FPM4 v10
   proposed, Tribe-Hotel-015 (Roberto avoids it). OpenStudio's `SpaceLoadInstance.makeUnique()` gives the
   load its own copy of the definition (checked on a synthetic case: original used by 1, the copy by 1,
   fractions and level kept).
2. **A load on a space type, which reaches every Space of that type.** Fact: reference-011 7 loads,
   FPM4 v10 proposed 35, Tribe-015 49. OpenStudio's `Space.hardApplySpaceType(False)` copies them onto the
   Space with Space totals unchanged (max change 0.0), but on reference-011 it also clones a space type per
   Space (7 -> 43, `Lobby` -> `Lobby 2`), writes inherited schedules onto the People (58 rows) and keeps the
   definitions shared (Office Lights Definition by 24 loads): 236 diff rows. A dedicated "unshare" step would
   copy each space-type load onto each Space, `makeUnique()` it, and remove it from the space type once
   every Space has its copy, keeping the Space's space type (schedule sets still apply).
   Not in v0.3 (not in the contract); proposed for v0.4.

## Item 8: results (session 2026-10-28, approved by Roberto: "ok 8", "ok" to units and source)

`results.zone_sizes / system_sizes / unmet_hours / end_uses(sql, units=None) -> polars.DataFrame`.
polars added as a regular dependency (2.1.0), imported only under `results/`.

- The SQL is opened read-only (`sqlite3`, `mode=ro`); sha256 unchanged after reading (evidence and test).
- Sizes from `ZoneSizes` / `SystemSizes` (full precision), not from the tabular report (rounded). Fact,
  FPM4 v10 proposed: zone `TZ-FPM4-N00.04-ARRUMOS` user design air flow 0.008 m3/s in the tabular report
  (= 28.8 m3/h) and 0.0083333 m3/s in `ZoneSizes` (= 30.0 m3/h); UTAN.05 5.26 vs 5.2597222 m3/s
  (18,936 vs 18,935 m3/h). Lost by this choice: setpoint, indoor temperature and humidity at peak (tabular only).
  A zone without sizing (FPM4 proposed `TZ-FPM4-NS1.09-10-ESTACIONAMENTO`, 0 W, design day N/A) is in the
  tabular report and not in `ZoneSizes`: 75 zones, not 76.
- Unmet hours and end uses exist only in the tabular report (2 decimals; GJ -> +-1.4 kWh). Units are read from
  the SQL's `Units` column, so an IP file gets IP column names (Roberto: users may run in IP).
  `ZoneSizes`/`SystemSizes` hold SI values per the EnergyPlus SQLite documentation (assumption: no IP file
