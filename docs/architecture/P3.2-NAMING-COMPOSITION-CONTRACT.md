# P3.2 Naming, Composition, And Evidence Contract

Status: Implemented and verified
Date: 2026-06-20
Baseline: `feature/agent-first-core` at `65b4461` plus uncommitted P3.1
Scope: Pure naming conformance, validator composition, and deterministic semantic QA/QC evidence

## 1. Objective

Complete the read-only toolkit vertical by converting an existing canonical `ModelInventory` into one deterministic geometry-validation report.

P3.2 adds no OpenStudio traversal, model mutation, workflow disposition, project Room mapping, artifact persistence, or release decision.

## 2. Boundary

### Toolkit owns

- Explicit `NamingProfile` validation.
- Naming checks derivable only from `ModelInventory` relationships.
- Composition of integrity, spatial, and optional naming validators.
- A semantic report linked to the canonical inventory hash.
- Canonical JSON serialization and a deterministic Markdown projection.
- Stable rule codes, ordering, and unit tests.

### Simulation OS owns

- Creation, selection, approval, and versioning of project naming profiles.
- Room register and Room-to-Space lineage reconciliation.
- Expected story, Space, and Thermal Zone mappings from project data.
- Finding disposition, exceptions, ownership, due dates, and rationale.
- Paths, runtime/run provenance, artifact registration, and human release gate.
- East Gate naming approval.

P3.2 checks model-visible conformance. It does not infer project intent.

## 3. NamingProfile

P3.1 introduced this strict schema:

```text
NamingProfile
  profile_id
  version
  status
  space_pattern
  one_to_one_zone_template
  multi_space_zone_pattern
  surface_separator
  subsurface_separator
  require_surface_sequence
  require_subsurface_sequence
```

### Semantics

- `status` is `draft` or `approved`.
- Regex fields use Python regular-expression syntax and always use full-string matching.
- `space_pattern` checks string shape only. It cannot prove source Room lineage.
- `one_to_one_zone_template` must contain `{space_name}` and produces one exact expected name.
- `multi_space_zone_pattern` checks the visible zone-name shape only. It cannot prove that all member Spaces are represented.
- Separators are literal strings, escaped before regex construction, and must be non-empty.
- A required sequence is a positive base-10 integer matching `[1-9][0-9]*`.
- Object types and boundary-condition tokens use the exact values already present in `ModelInventory`; P3.2 does not normalize SDK vocabulary.
- A draft profile is executable for preview and always emits `naming.profile.draft`.
- Missing grammar emits observations; it never activates a hidden toolkit default.

### Required schema hardening

- Reject empty separators.
- Reject a template containing unsupported replacement fields.
- Preserve existing regex compilation checks.

No exception list or per-object override is added to `NamingProfile`. Exceptions belong to Simulation OS disposition.

## 4. Naming Algorithm

Function:

```python
validate_model_object_naming(
    inventory: ModelInventory,
    profile: NamingProfile,
) -> list[Finding]
```

The function is pure and returns deterministically sorted findings.

### 4.1 Profile-level findings

| Code | Severity | Condition |
|---|---|---|
| `naming.profile.draft` | observation | Profile status is `draft` |
| `naming.profile.incomplete` | observation | Grammar needed by objects in the inventory is absent |

`naming.profile.incomplete` is one model-level finding with a sorted `missing_fields` evidence list. A missing multi-Space rule is reported only when at least one multi-Space zone exists.

### 4.2 Spaces

If `space_pattern` exists, evaluate `re.fullmatch()` for each named Space.

| Code | Severity | Condition |
|---|---|---|
| `naming.space.profile_mismatch` | minor | Space name does not fully match `space_pattern` |

Spaces without names are already reported by `integrity.name.missing`; naming does not duplicate that finding.

The result proves pattern shape only. Room-ID presence, ordering, grouping, and semantic label approval remain Simulation OS checks.

### 4.3 Thermal Zones

For a zone containing exactly one resolved Space:

```text
expected = one_to_one_zone_template.format(space_name=<actual Space name>)
```

Compare the full visible name exactly.

One-to-one detection uses the resolved zone membership from `ModelInventory`. If any listed Space handle is unresolved, naming skips the zone and leaves the structural defect to P3.1 integrity findings.

For a zone containing multiple Spaces, use `re.fullmatch(multi_space_zone_pattern, zone.name)` only when the pattern exists.

| Code | Severity | Condition |
|---|---|---|
| `naming.thermal_zone.one_to_one_mismatch` | minor | One-Space zone does not equal the rendered template |
| `naming.thermal_zone.multi_space_mismatch` | minor | Multi-Space zone does not fully match its profile pattern |
| `naming.thermal_zone.multi_space_rule_missing` | observation | A multi-Space zone exists but profile grammar is absent |

Empty zones and unresolved handles are left to P3.1 integrity/spatial findings. Naming does not fabricate an expected value from incomplete relationships.

### 4.4 Surfaces

Resolve the owning Space and, when present, the adjacent Surface and its Space.

For no adjacent modeled Surface:

```text
prefix = <owning Space><sep><Surface Type><sep><Outside Boundary Condition><sep>
```

For an adjacent modeled Surface:

```text
prefix = <owning Space><sep><Surface Type><sep><adjacent Space><sep>
```

The valid full name is `prefix + positive sequence`.

Diagnostic precedence prevents cascaded findings for one Surface:

1. If it does not start with `<owning Space><sep>`, emit `naming.surface.owner_mismatch`.
2. Else if it does not start with the exact derived `prefix`, emit `naming.surface.relationship_mismatch`.
3. Else if the suffix is not a required positive sequence, emit `naming.surface.sequence_missing`.

If required relationships or names cannot be resolved, integrity/spatial findings remain authoritative and naming skips that object.

Expected names are constructed from resolved relationship values and compared by exact prefix and suffix checks. The validator must never infer the owner, type, boundary, or adjacent Space by splitting a visible name on the configured separator. This construction invariant keeps names containing the separator and prefix-collision cases unambiguous.

Known limitation: if an adjacent Space name is byte-identical to an OpenStudio boundary-condition token, such as `Outdoors`, the derived visible prefix can be identical for two different relationships. P3.2 proves that the visible name matches the actual relationship-derived prefix, but cannot detect a stale relationship token when those two strings collide. This narrow ambiguity is accepted and documented rather than introducing an alias layer.

### 4.5 SubSurfaces

Resolve the parent Surface.

```text
prefix = <parent Surface name><sep><SubSurface Type><sep>
valid = prefix + positive sequence
```

Diagnostic precedence:

1. If it does not start with `<parent Surface name><sep>`, emit `naming.subsurface.parent_mismatch`.
2. Else if type or required sequence does not match the exact derived form, emit `naming.subsurface.type_or_sequence_mismatch`.

If the parent or its name cannot be resolved, naming skips the object because P3.1 already reports the structural defect.

As with Surfaces, the expected name is constructed from resolved values. The validator must never recover parent identity by splitting the visible name on the separator.

### 4.6 Deliberate exclusions

- Room-ID lineage and source ordering.
- Expected semantic Space label.
- Expected story or zone assignment from project registers.
- Space-Type and assigned-component naming.
- Surface/SubSurface renumbering order by geometry.
- Rename previews, change sets, or fixes.
- Cross-revision identity.

These require project data, broader inventory scope, or a controlled-mutation vertical.

## 5. Composition

Function:

```python
validate_geometry_inventory(
    inventory: ModelInventory,
    *,
    naming_profile: NamingProfile | None = None,
) -> list[Finding]
```

Rules:

- Always run integrity and spatial validators.
- Run naming only when an explicit profile is supplied.
- Never load a default profile from disk or environment.
- Preserve original severity and evidence.
- Remove only findings that are canonically identical in every field.
- Return the global deterministic `sort_findings()` order.

Absence of a naming profile means naming was not run, not that naming passed.

## 6. Semantic Validation Report

A released list of findings needs an explicit link to the semantic inventory and the checks actually executed.

```text
GeometryValidationReport
  schema_version
  inventory_sha256
  validator_suite
  validator_suite_version
  checks_run[]
  naming_profile_id
  naming_profile_version
  naming_profile_status
  findings[]
```

### Field rules

| Field | Rule |
|---|---|
| `schema_version` | Literal report-contract version, initially `0.1.0` |
| `inventory_sha256` | SHA-256 of canonical `ModelInventory` bytes |
| `validator_suite` | Stable literal `geometry-inventory` |
| `validator_suite_version` | Explicit ruleset version, initially `0.1.0` |
| `checks_run` | Sorted unique literals: `integrity`, `spatial`, optionally `naming` |
| naming profile fields | All null when naming was not run; all present when it was run |
| `findings` | Globally sorted findings produced by the composer |

The report is semantic and portable. It excludes absolute paths, interpreter paths, runtime module paths, timestamps, duration, user, disposition, and release status.

`schema_version` and `validator_suite_version` are mechanical contract versions, bumped only when report fields or rule behavior changes. They are not maturity states. Rule maturity remains owned by Simulation OS and its rule registry.

The `InventoryRun` envelope remains the source of run provenance. Simulation OS registers the report, run envelope, model revision, and human review together in P4.

## 7. Serialization And Human Projection

### Canonical JSON

```python
serialize_validation_report(report: GeometryValidationReport) -> ValidationArtifact
```

Use the same canonical rules as inventory serialization:

- UTF-8;
- sorted JSON keys;
- compact separators;
- `ensure_ascii=False`;
- reject NaN/Infinity;
- return exact bytes plus SHA-256;
- no implicit file write.

### Markdown projection

```python
render_validation_report_markdown(report: GeometryValidationReport) -> str
```

The deterministic projection includes:

- inventory hash and ruleset/profile identity;
- counts by severity;
- findings in canonical order;
- code, severity, object type/name/handle, message, evidence, and suggested action;
- an explicit `Naming not run` notice when no profile was supplied.

Markdown is a human view, not the machine source of truth. It contains no disposition columns because P4/Simulation OS adds workflow state.

Evidence is rendered as the same compact canonical JSON used by the machine serializer: sorted keys, UTF-8 characters preserved, and NaN/Infinity rejected. Markdown rendering never relies on Python dictionary display order or `repr()`.

## 8. Purity And Safety

P3.2 modules:

- import neither OpenStudio nor Pandas;
- access neither files, environment, clocks, nor network;
- do not mutate inventory, profile, or findings;
- do not write JSON or Markdown to disk;
- do not infer absent grammar or project mappings;
- do not suppress structural findings when naming cannot run for an object.

## 9. Acceptance Criteria

1. Profile regexes use full-string matching and separators reject empty values.
2. Draft and incomplete profiles emit deterministic observations.
3. One-to-one zones use exact rendered names; multi-Space zones never use an implicit rule.
4. Surface checks derive owner/type/boundary-or-adjacent-Space from actual relationships.
5. SubSurface checks derive parent/type from actual relationships.
6. One object emits at most one primary Surface or SubSurface naming mismatch under diagnostic precedence.
7. Objects with unresolved structural prerequisites are skipped by naming and remain represented by P3.1 findings.
8. Room-lineage conformance is neither claimed nor inferred.
9. Composer without a profile records only `integrity` and `spatial`; it never implies naming passed.
10. Report hash is portable across path/runtime envelopes for the same inventory, profile, and ruleset.
11. JSON and Markdown are deterministic; serializers do not write files.
12. Office Hub produces a report, but no naming-pass claim is made unless an explicit synthetic or approved profile is supplied.
13. East Gate naming is not executed or claimed until one profile revision is human-approved.
14. Legacy extractors, DataFrames, and task result schemas remain unchanged.
15. Full toolkit suite passes.

## 10. Test Matrix

- Schema: empty separators, invalid regex, unsupported zone-template field, partial report profile identity.
- Space: full match vs substring match, Unicode names, missing name dedup with integrity.
- Zone: exact one-to-one, multi-Space match/mismatch/missing rule, empty/unresolved zone skip.
- Surface: correct exterior, correct adjacency, stale owner, stale type/boundary/adjacent Space, invalid sequence.
- Surface ambiguity: adjacent Space literally named `Outdoors` versus exterior boundary token; lock the documented limitation.
- Surface construction safety: owner containing the separator and prefix-collision names such as `B2-0.1`/`B2-0.10`.
- SubSurface: correct inheritance, stale parent, stale type, invalid sequence.
- Composition: no profile, draft profile, exact dedup, stable ordering, inventory hash unchanged.
- Report: count-independent canonical bytes, profile/check consistency, portable semantic hash, Unicode, NaN rejection.
- Markdown: evidence dictionaries constructed in different key orders render byte-identically.
- Office Hub: integrity/spatial composition and deterministic report without naming claim.

## 11. Decisions Requiring Review

1. Approve `GeometryValidationReport` in the toolkit rather than deferring all report structure to P4.
2. Approve exact diagnostic precedence instead of emitting multiple derivative naming findings per object.
3. Approve exact SDK token matching without a normalization/alias layer in P3.2.
4. Approve full-match multi-Space zone pattern as shape-only, with traceability remaining Simulation OS-owned.
5. Approve deterministic Markdown as a toolkit projection while persistence/disposition remain Simulation OS-owned.
6. Confirm East Gate naming remains deferred.

## 12. Stop Boundary

P3.2 stops after schemas, pure validators, composer, serializers/projection, tests, and temporary evidence.

Do not add model mutation, naming fixes, Room mapping, CSV synchronization, MCP tools, CLI commands, containerization, or Simulation OS release logic.
